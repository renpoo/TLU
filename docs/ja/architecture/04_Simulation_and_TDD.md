# 04. シミュレーションとテスト駆動開発 (Simulation and TDD)

監査システムである Tensor-Link Utility (TLU) の計算ロジックは、常に正確であることが求められます。実務の現場でアルゴリズムを信頼して使用するためには、あらゆる異常パターンに対して正しく警告を発することを、継続的にテストし証明しなければなりません。

この「シミュレーション」機能は、複雑な取引ネットワークを人工的に生成し、TLUのコア解析フィルターが正しく動作するかを厳格にテスト（検証）するためのものです。

---

## 1. 人工的なテストデータが必要な理由

現実の複雑な会計データだけを見ていると、アルゴリズムの計算結果が本当に正しいのか（検知漏れや誤検知がないか）を判断するのは困難です。システムの正確性を証明するためには、あらかじめ「どこにどのような異常があるか」という正解が分かっているテストデータ（合成データ）を作成し、TLUがその異常を正確に検知・指摘できるかを確認する必要があります。

## 2. シミュレーションの実行モード

### ベースラインモード（正常系のテスト）
* **仕組み:** 一定のリズムで流れる、全く異常のない取引ストリームを生成します。
* **目的:** このモードでは、TLUは「異常なし」と判断しなければなりません。正常な状態のネットワークに対して、システムが誤って警告を出さないこと（誤検知の防止）を検証します。

### リアルビジネスモード（現実の模倣）
* **仕組み:** 実際の企業活動に近い、複雑な取引ネットワークを模倣します。
* **特徴:** 取引が集中する特定の口座（ハブ）の形成や、定期的な景気の波など、実務データによく見られる偏りを持たせたテストデータを作成します。

## 3. 意図的な異常データの注入（不正検知のテスト）

TLUが帳簿の改竄や横領などの不正を正確に検知できることを証明するため、シミュレーターは生成した正常なデータに対して、決定論的（意図的）に異常な取引データを混入させます。

* **局所的な異常（Z-Score）のテスト:** 特定の口座・特定の日に、極端に巨大な取引金額を強制的に書き込み、3Dサーフェス上で鋭い異常値として検知できるかを確認します。
* **資金流用（構造変化）のテスト:** 全体の取引額は変えずに、取引の「宛先」だけを密かに書き換えます。これは、目立たないように資金を着服する「横領」を模倣し、システムが構造的変化として検知できるかを検証します。
* **質量保存の法則の違反（マクロ異常）のテスト:** 対応する「支払い」が存在しない「入金」だけを人為的に発生させ、貸借一致の原則が破綻したこと（架空計上など）を検知できるかを確認します。
* **循環取引（システム不安定化）のテスト:** 意図的に資金がA→B→C→Aと循環するループ取引を注入し、システム安定性（スペクトル半径）の指標が危険水域に達することを確認します。

## 4. 自動テスト（CI/CD）との統合

シミュレーターは完全に自動化されており、TLUの開発プロセス（自動テストスイート）に直接組み込まれています。コアとなる数学関数や計算ロジックが更新されるたびに、これらの合成された異常データが自動的にシステムに流し込まれ、常にバグや検知漏れがない状態が保たれるよう設計されています。
