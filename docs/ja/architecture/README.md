# TLU システム・アーキテクチャと運用思想 (Architecture & Operations)

## 🔬 結論先行：TLUのシステム設計が証明する「究極の客観性」

本ディレクトリ（`architecture/`）の最大の結論は、**「監査・フォレンジックツールにおいて、どんなに高度な数学モデルを用いても、その計算プロセスに『ブラックボックス』や『人間のバイアス（恣意性）』が混入する余地があれば、証拠としての価値はゼロである」**という厳格な設計思想です。

TLU（Tensor-Link Utility）のアーキテクチャは、「入力データが同じであれば、誰が、いつ、どこで実行しても、必ず100%同じ異常検知結果（グラフ）が出力されること（再現性と反証可能性）」をソフトウェア工学的に保証するために構築されています。

---

## 📚 ドキュメント構成（パイプライン・アプローチ）

TLUがどのようにして「客観性」と「再現性」を担保しているか、その設計哲学と運用ルールを以下のドキュメントで解説します。

### 1. 思想とデータ構造（システムの土台）
* **[01. システム哲学と運用](01_System_Philosophy_and_Operations.md)**
  * **内容:** コンテナ化とUnix哲学による、ローカル環境に依存しない「ステートレス」なパイプライン設計の全貌。
* **[02. データ構造と射影](02_Data_Topology_and_Projection.md)**
  * **内容:** バイアスを排除するため、勘定科目名などの「言葉」を剥奪し、純粋なテンソル空間へとデータを強制翻訳（射影）するメカニズム。

### 2. デザインとインターフェース（人間の認知ハック）
* **[03. 可視化・テーマ・エンジン](03_Visualizer_and_Theme_Engine.md)**
  * **内容:** 高次元の数学的異常を、人間の脳が直感的に「痛み」として認識できるよう設計された、シネマティックな可視化エンジンの美学。
* **[05. メタ診断手法とAIの協働](05_Meta_Analytical_Methodology_and_AI_Collaboration.md)**
  * **内容:** 計算機（決定論）とAI（確率論）を厳格に分離し、AIを「計算者」ではなく「診断医（ナラティブ・ジェネレーター）」として扱う協働プロトコル。

### 3. TDDと証明のライフサイクル（テストと限界）
* **[04. シミュレーションとテスト駆動開発](04_Simulation_and_TDD.md)**
  * **内容:** 「意図的に仕込んだ不正」を確実に検知できるかを自動証明し続ける、テスト駆動開発（TDD）の哲学。
* **[06. ダミーデータ生成エンジン](06_Dummy_Data_Generators.md)**
  * **内容:** 異常を定義するための比較原器となる「一切のノイズを含まない無菌状態のベースライン（Sample 0）」の生成ロジック。
* **[07. 理論的限界とエッジ・エフェクト](07_Theoretical_Limits_and_Edge_Effects.md)**
  * **内容:** データの極度な不足（初期状態など）によって生じる数学的限界（偽陽性）と、それを監査人に警告するシステムの誠実さ。
