# 01. システム哲学と運用 (System Philosophy and Operations)

Tensor-Link Utility (TLU) は、複雑で肥大化したシステム設計を避け、**Unixの哲学（ひとつのプログラムにはひとつの機能を持たせ、それらを連携させる）**に基づいたシンプルで堅牢なアーキテクチャを採用しています。

本ドキュメントでは、TLU（Ver 1.0.0）の設計原則と運用上のルールについて解説します。

---

## 1. パイプライン・アーキテクチャ

TLUは、企業の財務データを一連の「データストリーム（連続した情報の流れ）」として処理します。

* **ステートレスなフィルター設計:** 各解析フィルター（熱力学解析、運動学解析など）は独立したプログラムとして動作します。標準入力からテンソルデータを受け取り、単一の物理数学モデルによる計算結果を列として追加し、標準出力へと渡します。
* **内部状態（隠し状態）の排除:** 各フィルターはデータベースやメモリ上に過去の実行状態を保持しません。入力データが同じであれば、常に同じ出力が返されることが数学的に保証されます。
* **パイプ連携 (`|`):** 巨大で複雑なプログラムを作るのではなく、シンプルな機能を持つフィルター群をパイプで連結することで、高度な異常検知を実現しています。

## 2. 役割の明確な分離（入出力と計算ロジック）

テストの正確性を高め、開発者の負担を減らすため、TLUでは「データの入出力」と「数学的な計算処理」を物理的に分離しています。

* **ラッパー層 (`filter_*.py`):** コマンドライン引数の処理、CSVファイルの読み書き、勘定科目名などの文字列処理のみを担当します。**この層に計算ロジックやビジネスルールを含めることは厳格に禁止されています。**
* **コア数学層 (`core_*.py`):** 純粋な数学関数のみを定義した層です。CSVの形式や会計用語を一切認識せず、純粋なテンソル配列のみを受け取って計算結果を返します。これにより、計算の厳密性が担保されます。

## 3. 実行環境の完全な分離（ローカル依存性ゼロ）

監査ツールにおいて「特定のPC環境でしか動かない」という事態は許容されません。

* **コンテナ化による隔離:** ユーザーのPC（ホストOS）に必要なのは `Docker` と `bash` 環境のみです。PythonやNumPyなどの実行に必要なライブラリは、すべて Docker の `tlu-engine` コンテナの内部に隔離されています。
* **透過的な実行 (`_tlu_env.sh`):** ユーザーはコンテナの存在を意識することなく、ローカルのスクリプトを実行するだけで自動的にコンテナ内で処理が行われます。

## 4. 設定ファイルの集中管理（SSOT）

複雑なデータ解析において、「どの設定で実行した結果か」を後から証明できることは、解析結果そのものと同じくらい重要です。TLUではこれを保証するため、設定の単一情報源（Single Source of Truth）を採用しています。

* **`_sys_params.csv` による一元管理:** 分析対象のデータソース、対象ノード、異常判定の閾値などを変更するために、ソースコードを直接書き換えることは禁止されています。すべての実行条件は、`workspace/config/_sys_params.csv` という単一の設定ファイルで定義されます。
* **実験の設計図:** このファイル自体が、分析条件を正確に記録した設計図（監査証跡）として機能します。

## 5. 実行履歴のスナップショットと再現性

監査の透明性を担保するため、TLUは過去の実行状態を完全に保存・再現する機能を備えています。

* **ワークスペースのアーカイブ保存:** 解析パイプラインの実行後、`bash bin/archive_experimental_run.sh` を実行するだけで、`workspace/` フォルダ全体（入力データや設定ファイルを含む）がスナップショットとしてアーカイブ保存されます。
* **過去の実行状態の完全再現:** 保存されたアーカイブ・ディレクトリを指定して再度実行することで、当時の設定と全く同じ条件でパイプラインが動作し、以前の解析結果を寸分違わず再現・再検証することが可能です。
